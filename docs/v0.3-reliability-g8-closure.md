## Fixes

### R1 — remote object identity

CarbonData documentation confirms that CTAS supports `TBLPROPERTIES` and that
`DESC FORMATTED` exposes table metadata. CarbonLens now:

1. Generates an unpredictable per-table `carbon_lens_ownership_token`.
2. Injects that token into the managed CTAS statement as a Carbon table property.
3. Stores the token in `managed_tables` with the table reservation.
4. Requires `DESC FORMATTED` metadata to contain the same token before a CTAS
   becomes `active` and before INSERT completion is accepted.
5. Rejects missing metadata, missing tokens, and token mismatches with
   `OWNERSHIP_UNVERIFIED`; a name, schema, or `cl_tmp_` prefix alone is not proof.
6. Checks identity before DROP and verifies absence after DROP. A replacement
   with the same name is not accepted as the original object.

The implementation deliberately does not claim a physical database/RBAC
boundary. A Carbon administrator able to rewrite table properties remains an
infrastructure-level risk; the application fails closed when it cannot read or
match the marker.

Primary dialect references:

- [CarbonData CTAS and TBLPROPERTIES](https://github.com/apache/carbondata/blob/master/docs/ddl-of-carbondata.md)
- [CarbonData DESC FORMATTED table-property example](https://github.com/apache/carbondata/blob/master/docs/streaming-guide.md)

### R2 — SQLite local atomicity

CTAS execution metadata and its managed-table reservation are inserted in one
SQLite `BEGIN IMMEDIATE` transaction. If either insert fails, the transaction
rolls back both records and remote submission is not attempted. The subsequent
`starting` transition is intentionally separate: a process crash before remote
submission leaves a durable queued/reserved record that can be observed without
guessing or replaying the write.

When a remote INSERT is uncertain, the target transitions to `insert_unknown`;
the target is no longer accepted as an active write target until reconciliation.
There is no automatic retry or compensating write.

## Guardrail evidence

- Original, third-party, unregistered, cross-workspace, and token-mismatched
  targets are rejected before remote write submission.
- Existing read/query/export tools remain on the read-only path.
- CTAS reservations are persisted before remote start.
- Remote completion is not inferred from a local timeout or missing status file.
- The only live Carbon calls in this closure were `carbon_list_connections`,
  `DESCRIBE`, and `DESC FORMATTED` read-only checks. No business rows were
  requested and no write SQL was issued.

## Fault injection

`tests/test_executions.py` covers:

- failure before the execution insert;
- failure while inserting the managed-table reservation;
- proof that both SQLite tables remain empty after either failure;
- proof that the remote detached start count remains zero;
- remote ownership-token mismatch before INSERT;
- remote failure and unsupported-dialect classification;
- cancellation racing with remote success;
- missing remote status becoming `unknown` without resubmission;
- unknown INSERT quarantining the target;
- new manager recovery from the same SQLite DB without a second remote start;
- same-key idempotency and conflicting-request rejection.

## G8 live evidence

Status: **`BLOCKED_ENV`**.

The live connection inventory contained one configured connection. A
credential-safe local configuration inspection reported:

```text
write_workspace.enabled = false
write_workspace.schema = <empty>
write_workspace.table_prefix = cl_tmp_
```

The read-only Carbon smoke checks succeeded for connection selection and
`DESCRIBE`/`DESC FORMATTED` metadata access. The formatted output had the
expected `col_name`, `data_type`, and `comment` shape, which is sufficient to
exercise the parser once a dedicated workspace is authorized. It did not prove
custom-token visibility on a CarbonLens-created table because no such table was
created.

The following G8 steps were therefore not run:

1. create isolated CTAS;
2. read back the marker and one constant row;
3. INSERT INTO;
4. INSERT OVERWRITE;
5. restart and recover the same execution/registry;
6. DROP and verify absence;
7. clean up only this run's registered table.

No G8 PASS is claimed. To close G8, an operator must first configure and
explicitly authorize an isolated workspace whose schema is different from
business schemas, then repeat only the bounded sequence above with a fresh
idempotency key and retain redacted execution evidence.

## Remaining risks

1. The live Carbon deployment has not yet confirmed that a custom property
   appears in its CTAS `DESC FORMATTED` output. If it does not, the application
   will reject ownership as designed; the dialect adapter must then be adjusted
   only after controlled confirmation.
2. The application-level token is not equivalent to an underlying Carbon
   object ID or database privilege boundary.
3. C5 native Beeline reconciliation and C6 performance/SLA remain explicitly
   `WAIVED / OUT OF SCOPE`.
4. No credentials, keytabs, private keys, raw SSH diagnostics, or business rows
   are included in this report.
